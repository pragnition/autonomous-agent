# Task Record and Task KPIs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Core labels every request the agent answers (chat / new task / same task) with Haiku, keeps a permanent
task record the agent can read through a skill, and the KPIs become four numbers computed from that record.

**Architecture:** Turns carry their source, requester and parent from the moment they are queued. A background
labeler in core (after each result, plus a 5-minute sweep) asks Haiku through the Claude proxy for each finished,
unlabeled request, writes `request_labels`, rebuilds the touched row of `task_records`, and rewrites that month's
`/data/tasks/YYYY-MM.jsonl`. KPIs, the digest, the CLI, the `kpis` tool and the dashboard read `task_records`,
`agent_prs` and `linear_issues`.

**Tech Stack:** Python 3.12, aiohttp, httpx, SQLite; React + TypeScript + TanStack Query + Recharts dashboard; a
Claude Code plugin skill (Markdown).

**Spec:** `docs/superpowers/specs/2026-11-15-task-kpis-design.md`

## Global Constraints

- Labeling never touches a turn: nothing in the labeler runs before a turn starts, and nothing it raises reaches
  `on_result`, reactions, replies or retries.
- Model: `claude-haiku-4-5`, through the proxy's `/v1/messages` at core's `PROXY_URL`, headers
  `authorization: Bearer sk-ant-oat01-container-via-host-proxy` (`agent.proxy.PLACEHOLDER_TOKEN`),
  `anthropic-version: 2023-06-01`, `anthropic-beta: oauth-2025-04-20`, `x-claude-code-session-id: <uuid>` (one uuid
  per sweep). Verified live: both 28090 and 28091 answer 200.
- Before each sweep makes a call, `await proxy.usage()` must report `has_capacity()`; otherwise the sweep ends.
- Labels: `chat` | `new` | `same`. Sources: `slack` | `linear` | `schedule`. Task ids: `TK-0001`, `TK-0002`, … (never
  `T-`, which the old `tasks` table uses).
- Context per call: up to 5 earlier labeled requests in the conversation; the requester's other tasks with a request
  in the 24 hours before this one, up to 10. Request text trimmed to 2000 characters, reply to 3000, `asked` in a
  step to 300.
- After 3 unparsable answers a request is labeled `chat` with `finished` NULL. A transport error (proxy down, 429,
  5xx) doesn't count as a try.
- Smoke-test conversations (`conversation_id LIKE 'V-smoke%'`) are never labeled.
- Agent copy: `/data/tasks/YYYY-MM.jsonl` by the task's start in the config timezone, newest first, written to a temp
  file then renamed. Mounted read-write in core, read-only in the agent container.
- KPI text form (exact):
  ```
  {name}, last {days} days
  Tasks: 12 (Slack 9 · Linear 3 · schedules 0)
  Time per task: median 6m · p90 41m
  Finished: 83% (10 of 12)
  Shipped: 0 PRs merged · 0 Linear issues closed
  ```
  With no tasks: `Time per task: n/a` and `Finished: n/a (0 of 0)`. "1 day" when days is 1.
- No Claude cost anywhere. No per-project filter. Commits: conventional prefix, no co-author or tool trailer.

## Review Focus

1. Haiku wraps its JSON in a ```` ```json ```` fence or adds a sentence before it → still parsed (Task 3 test).
2. The proxy is down or answers 429 in the middle of a sweep → the sweep stops, no request's `tries` goes up, the
   next sweep picks up where it stopped (Task 3 test).
3. A request with no text (a file-only Slack message, the empty-text turn seen live) or a reply with no text (an
   errored turn) → still labeled; Haiku sees `(no text)` (Task 2 test on the context).
4. Haiku answers `same` with a task id it wasn't offered, or `new` without a title → `new` with the request's first
   60 characters as the title (Task 3 test).
5. The tasks folder isn't writable → the export logs and the labels are still saved (Task 2 test).

- Produces:

    `finished: bool | None`.
  - `pending(conn) -> list[sqlite3.Row]`: finished (`status IN ('done','failed','cancelled')`), `kind = 'turn'`,
    non-smoke work items with no labeled `request_labels` row, by `created_at, rowid`. Columns: `id`,
    `conversation_id`, `payload`, `result`, `status`, `created_at`, `updated_at`.
  - `origin_of(conn, config, row) -> tuple[str, str | None, str | None]`: `(source, requester, follows)`. Payload keys
    win. Otherwise: a conversation in `linear_issue_conversations` or text starting `Linear agent session event:` →
    `linear` (requester from the webhook JSON in the text, as in Task 1); origin starting `[schedule` → `schedule`;
    else `slack` with `actor`. `follows` for an old continuation (`payload.continuation > 0`) is the previous work
    item of the same conversation.
  - `RequestContext` dataclass: `asked: str`, `reply: str`, `errored: bool`, `earlier: list[dict]`,
    `recent: list[dict]`; and `context_for(conn, row, requester) -> RequestContext`. `earlier` items:
    `{"task": id|None, "label", "title", "asked"}`. `recent` items: `{"task", "title", "outcome"}`. For a Linear turn,
    `asked` is `"<KEY> <title>: <prompt body or comment body>"` from the webhook JSON.
  - `apply_label(conn, row, label: Label, *, source, requester, follows, tz: str) -> str | None`: writes the
    `request_labels` row (allocating `TK-NNNN` for `new`), rebuilds that task, returns its id (None for chat).
  - `rebuild_task(conn, task_id) -> None` and `task_record(conn, task_id) -> dict`.
  - `work_seconds(intervals: list[tuple[str, str]]) -> int`: the union of `[start, end)` intervals in seconds.
  - `export_months(conn, tasks_dir: Path, months: set[str], tz: str) -> None` and
    `month_of(started_at: str, tz: str) -> str`.

Schema (in `SCHEMA`):

```sql
-- The labeler's verdict on each request the agent answered (tasks and KPIs)
CREATE TABLE IF NOT EXISTS request_labels (
    work_item_id TEXT PRIMARY KEY,
    conversation_id TEXT,
    source TEXT NOT NULL,
    requester TEXT,
    follows TEXT,
    asked TEXT NOT NULL DEFAULT '',
    link TEXT,                -- the origin line's URL: the Slack permalink or the Linear issue
    label TEXT,               -- chat | new | same; NULL until labeled
    task_id TEXT,
    outcome TEXT,
    finished INTEGER,
    arrived_at TEXT NOT NULL, -- the work item's created_at
    started_at TEXT,          -- its latest session_started
    answered_at TEXT,         -- its updated_at once finished
    tries INTEGER NOT NULL DEFAULT 0,
    labeled_at TEXT
);
CREATE INDEX IF NOT EXISTS request_labels_task ON request_labels(task_id);
CREATE TABLE IF NOT EXISTS task_records (
    id TEXT PRIMARY KEY,      -- TK-0001
    source TEXT NOT NULL,
    requested_by TEXT,
    started_at TEXT NOT NULL,
    ended_at TEXT,
    jensen_time_s INTEGER NOT NULL DEFAULT 0,
    finished INTEGER,
    record TEXT NOT NULL      -- the whole record as JSON, as exported
);
CREATE INDEX IF NOT EXISTS task_records_started ON task_records(started_at);
```

The record (`task_record`, the `record` column and each export line):

```json
{"id": "TK-0012", "title": "…", "source": "slack", "requested_by": "sam", "followed_up_by": ["alex"],
 "where": ["https://…slack.com/archives/…"], "started_at": "2026-11-15T03:34:19Z", "ended_at": "…",
 "jensen_time_s": 720, "requests": 3, "finished": true, "outcome": "…", "links": ["https://github.com/o/r/pull/12"],
 "steps": [{"at": "…", "by": "sam", "asked": "…", "outcome": "…", "finished": true, "work_item": "W-…"}]}
```

`where` is the distinct `link`s of its requests (the URL in each payload's origin line). `links` is every distinct
GitHub PR URL (`https://github.com/<o>/<r>/pull/<n>`) and Linear issue URL (`https://linear.app/<ws>/issue/<KEY>…`)
found in the tasks' reply texts. `jensen_time_s` is `work_seconds` over each request's `(started_at or arrived_at,
answered_at)`. `title` is the `new` request's title; `outcome`/`finished` are the latest labeled request's.

### Task 3: The labeler

**Files:**
- Create: `src/agent/core/task_labeler.py`
- Test: `tests/test_task_labeler.py`

**Interfaces:**
- Consumes: Task 2's `pending`, `origin_of`, `context_for`, `apply_label`, `export_months`, `month_of`, `Label`.
- Produces:
  - `parse_label(text: str) -> Label | None` (tolerates a code fence or prose around one JSON object; None when
    there's no valid object or `label` isn't one of the three).
  - `class HaikuUnavailable(Exception)`.
  - `make_haiku(base_url: str, http: httpx.AsyncClient | None = None) -> Callable[[str, str, str], Awaitable[str]]`:
    `complete(system, user, session_id)` → the reply's text; raises `HaikuUnavailable` on transport errors, 429 and
    5xx.
  - `class TaskLabeler(conn, config, *, complete, has_capacity: Callable[[], Awaitable[bool]], tasks_dir: Path,
    concurrency: int = 4, max_tries: int = 3)` with `async sweep() -> int` (requests labeled) and `poke() -> None`
    (starts a sweep in the background unless one is running).

Sweep algorithm (the part the tests don't fully pin):

```
rows = pending(conn); if none: return 0
if not await has_capacity(): return 0
group rows by requester (origin_of), keeping arrival order; one session uuid for the sweep
for each group, concurrently (asyncio.Semaphore(concurrency)):
    for row in group:
        source, requester, follows = origin_of(...)
        parent = request_labels row of `follows` if any
        if parent has a task: fixed label "same" -> parent.task_id (Haiku still asked; its label/task ignored)
        call Haiku with PROMPT + context; on HaikuUnavailable: stop this group (no try counted)
        parsed = parse_label(reply)
        if parsed is None: tries += 1; if tries >= max_tries: label chat; else stop this group
        fix up: same with an unoffered task -> new; new without title -> asked[:60] or "Untitled"
        apply_label(...); collect the touched task's month
export_months(conn, tasks_dir, months, config.timezone)
```

`PROMPT` (system) says: you sort the requests a team sends their AI engineer; answer with one JSON object only;
the field meanings from the spec's table, word for word, including the `finished` definition; `task` must be one of
the ids listed.

````markdown
# Task history

Core keeps a record of every task you've done, from Slack, Linear and schedules. It writes it to
`/data/tasks/YYYY-MM.jsonl` (read-only for you): one file per month by when the task started, one task per line,
newest first. Chat (greetings, small talk) isn't recorded. A request shows up about 5 minutes after you answer it.

Each line has: `id`, `title`, `source` (slack, linear, schedule), `requested_by` and `followed_up_by` (person keys,
or a Linear name), `where` (the Slack thread or Linear issue), `started_at` and `ended_at` (UTC), `jensen_time_s`
(your working time, not waiting on people), `requests`, `finished`, `outcome`, `links` (PRs, issues) and `steps`
(each request: `at`, `by`, `asked`, `outcome`).

## Answering

1. Pick the months the question covers (`ls /data/tasks`). The team's timezone is in `/run/agent/timezone`;
   convert times to it when you answer.
2. Filter with `jq`; never print a whole file. For example:

   ```bash
   jq -c 'select(.started_at >= "2026-11-10") | {id, title, requested_by, finished, outcome}' /data/tasks/2026-11.jsonl
   jq -c 'select(.requested_by == "sam" and .finished != true) | {id, title, outcome}' /data/tasks/2026-11.jsonl
   jq -c 'select(.title + " " + ([.steps[].asked] | join(" ")) | test("debloat"; "i")) | {id, title, where}' /data/tasks/*.jsonl
   ```
3. Answer from the record: name the work, who asked, when, whether it's finished, and link the thread, issue or PR.
   If the record has nothing, say so plainly instead of guessing.
````
